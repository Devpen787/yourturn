# Exact operation output retention

Claim #16 5648160041. `feature/ethonline-ledger-retained-output-qual` starts from independently cleared881cfc7d. Existing current/operation/owned-loader/World/Hedera source and dependencies are unchanged.

The World consumer can atomically begin an effect before calling Hedera's irreversible payment reservation. If preparation succeeds but its response is lost, it must not prepare again. `retainPreparedRecoveryOutput` gives the trusted preparer a permanent, write-once store for the exact output before returning its references. It accepts only an exact existing effect-started operation, native transaction ID reference and canonical base64 bytes (1–65,536 bytes); computes SHA-256 internally; validates operation identity/intent/fence/revision; and compares the complete operation record atomically with the retained artifact write. Exactly identical bytes/ID are idempotent. Any different output conflicts. No TTL, overwrite or delete exists.

This module deliberately treats bytes as **opaque retained evidence**. It does not certify that they encode a native transaction, the stated transaction ID or authorized economics. The trusted Hedera preparer and external-signing verifier must establish those facts. Retention never constructs, signs or submits a transaction and always returns executionPermit:false. Neither authenticated identity nor current authority may be inferred from a retained blob.

`readRetainedRecoveryOutput` requires server-authenticated owner/operation/full intent, reparses exact schema and canonical bytes/digest, matches current durable operation identity and any existing transaction/digest references, and repeats operation/artifact reads to catch drift. A missing output stays missing; no preparation retry occurs. No raw output or signatures are logged by this module.

`attachRetainedRecoveryOutput` invokes the existing fenced/leased record-envelope transition using only the stored exact references. A stale worker cannot attach. Retaining late-arriving output after expiry/revocation is allowed solely to preserve evidence; attachment requires the current lease. The existing receipt-only takeover can obtain a fresh fence for an already-started operation, then attach its already retained exact output and reconcile a trusted receipt. That flow cannot begin another effect or restore expired/revoked economic authority. Completion after expiry/revoke does not make the original bytes usable for new signing/submission.

If EVAL throws or returns an unexpected result, the API reports RETENTION_OUTCOME_UNKNOWN_RELOAD_REQUIRED. A write may already exist. The caller must reload exact retained output rather than regenerate it, abandon the started operation or clear payment tombstones. Atomicity covers the operation/output records in this Redis store, not external signing, chain execution, provider policy or actor provisioning. Deployed Redis backup/retention/access configuration remains an operational requirement.

Focused local/model tests cover concurrent same/conflicting outputs, malformed/tampered/oversized bytes, wrong identity/fence/revision, unknown-after-write recovery, expiry/revoke followed by receipt-only takeover, and immutable references. Hosted tests run the same matrix against actual disposable Redis Lua and verify no TTL. Synthetic opaque bytes are explicitly not native transaction proof. Existing actual activation/claim/owned-authority tests run separately as regressions. No secrets, device interaction, real World or Hedera credentials, economic signing or funds are used.
